# Reconfigurable Assembly Line — Digital Twin & Simulator

A Python simulation + Streamlit dashboard for the six-station VIPER / Innovation Factory
manual assembly line, built around the idea in *Reconfigurable Assembly Line and Sensor
Architecture*:

> describe the manufacturing system **once**, in a structured, machine-readable way, so the
> same description drives the physical testbed, the digital twin and the simulation —
> even when the line changes.

Nothing about the line is hard-coded in Python. Two files define it:

| File | Holds | Examples |
|---|---|---|
| `configs/line_config.yaml` — **configuration file** | **Structure**: objects + relationships | stations, processes, operators, components, subassemblies, bins, load cells, cameras, buffers, routing |
| `configs/line_data.yaml` — **data file** | **Behaviour**: times + distributions + measurements | process-time distributions, defects, operator variability, failures, part weights, bin stocking, refill lead time, load-cell & camera specs |

A reconfiguration is an **edit of relationships** in the configuration file. The simulator,
the sensor pipeline and the dashboard read the new relationships; no code changes.

## 1. The configuration file (structure)

```yaml
routing: [S1, S2, S3, S4, S5, S6]            # product flow; a list = parallel stations, e.g. [S3, S3B]

buffers:
  BUF1: {from: S1, to: S2, capacity: 1}       # missing buffer = direct hand-off (capacity 0)

stations:
  S3: {operator: O3, camera: CAM_S3, processes: [P3, P4]}   # Process -> Station (ordered)

processes:
  P3: {inputs: {SA2: 1, C10: 1, C09: 2}, output: SA3}      # consumes components/subassemblies, produces SA3
  P4: {inputs: {SA3: 1, C07: 1, C08: 1}, output: SA4}      # SA3 becomes an input to P4

bins:
  B35: {station: S3, component: C10}          # Bin -> Station, Bin -> Component (null = empty slot)

sensors:
  LC_35: {type: load_cell, measures: B35}     # stable sensor ID -> the bin it measures
  CAM_S3: {type: camera, station: S3}
```

**ID convention.** Station *n*, slot *k* → bin `B<n><k>`, load cell `LC_<n><k>`. So `LC_35` is
the 5th load cell of Station 3. If bin B35 is re-stocked with C21, only `B35 contains C21` changes;
the sensor is still `LC_35` (see `configs/variants/alt_bearing_C21.yaml`).

**Validation** (blocks the simulation on errors) checks, among others:

- every routed station has a declared operator; cameras are camera sensors;
- every process is performed at exactly one stage; parallel stations perform the same processes;
- **material availability** — each component a process consumes is in a bin *at that station*;
- **precedence** — a subassembly is produced upstream (or earlier at the same station);
- each subassembly is produced by exactly one process; there is a final product;
- a bin is measured by at most one load cell; buffers connect neighbouring stages;
- warnings for bins without load cells, more bins than physical slots, pass-through stations;
  notes for shared operators and spare stock.

### Reconfiguration operations (UI tab *Reconfigure*, or `line_sim.config_model`)

| Operation | Function | What changes |
|---|---|---|
| Move a process to another station | `move_process(cfg, "P3", "S2")` | `P3 performed_at S2`; optionally frees the old bins and re-points free bins at S2 to P3's components |
| Change what a bin contains | `set_bin_component(cfg, "B35", "C21")` | `B35 contains C21` (sensor keeps its ID) |
| Re-point a load cell | `set_sensor_bin(cfg, "LC_35", "B34")` | `LC_35 measures B34` |
| Operator assignment / sharing | `set_station_operator(cfg, "S6", "O5")` | `O5 operates S6` (O5 now serves S5 + S6) |
| Buffer capacity | `set_buffer_capacity(cfg, k, 4)` | buffer between stage k and k+1 |
| Parallel station | `add_parallel_station(cfg, "S3")` | clones S3 as S3B with its own operator, bins, load cells, camera |
| Add / remove station | `add_station(...)`, `remove_station(...)` | routing, buffers, bins, sensors |
| Swap a recipe input | `replace_process_input(cfg, "P3", "C10", "C21")` | `P3 consumes C21` |

Each returns `(new_config, messages)`. `diff_relationships(before, after)` produces the
before/after table from the document (e.g. `P3 performed_at: S3 → S2`, `B35 contains: C10 → C21`).

## 2. The data file (behaviour)

Keyed by **object ID**, never by position — a process that moves keeps its own time data.
Missing entries fall back to the section's `default`.

- `process_times` — per process: `lognormal | normal | gamma` (mean, cv), `exponential` (mean),
  `triangular` (min, mode, max), `uniform` (min, max), `constant` (value), `empirical` (samples)
- `pick_window` — picks happen in the first fraction of a process (first pick at t = 0)
- `defect_probability` — per process (first-pass-yield model)
- `operators` — `speed_factor` (1.10 = 10 % slower), `cv_factor`
- `failures` — per station: `mtbf_s` (busy time) and `repair_time` distribution
- `components` — `unit_weight_g` (what a load cell sees per part)
- `bins` — per component: `capacity_units`, `reorder_point_units`, `tare_g`
- `replenishment.lead_time` — reorder point → refilled bin
- `load_cells`, `camera`, `pick_detection` — sensor characteristics and detector settings

## 3. The simulation

A discrete-event model **built from** the two files. Per unit and station:

1. the station needs an input unit (stage 1 always has one; later stages take from the upstream
   buffer, or directly from a blocked upstream station when there is no buffer), its operator
   free, and no pending failure;
2. for each process at the station a time T is drawn; the operator picks each component from its
   bin (first pick at t = 0, others spread over `pick_window × T`) — the bin's weight drops,
   which is what the load cell sees; an empty bin makes the station **wait for material**;
3. the camera reports `unit_complete`; the unit moves on or the station is **blocked**.

Bins at the reorder point are refilled after a random lead time. Shared operators serve one
station at a time (downstream first). Failures are counted in busy time and occur between units.

**Station states:** working · waiting for material · down · waiting for operator · blocked · starved.

**KPIs (after warm-up):** throughput, completed units, first-pass yield, lead time (mean, p50, p90),
average WIP (with a Little's-law check), utilisation, blocking/starvation, bottleneck, operator
utilisation, buffer occupancy, refills and stock-outs, plus an **analytic upper bound** from mean
times, parallelism, shared operators and availability.

**Bottleneck** = station with the highest *active* share (working + down + waiting for material),
i.e. the one that is least often blocked or starved — not simply the longest mean time.

**Common random numbers.** Each process, station, camera and the material handler has its own
seeded random stream, and replication *r* uses the same seed in every configuration, so
comparisons between configurations reflect the structure, not luck.

## 4. Sensors (the three phases of the document)

| Phase | In the code | In the app |
|---|---|---|
| 1 Connectivity | `synthesize_load_cell_signals` (from the simulation: sample rate, noise, drift, hand-contact spikes) or `read_signal_csv` (real testbed) | raw weight per sensor, with true vs detected picks |
| 2 Pick detection | `detect_steps` / `detect_all`: a change > max(0.5 × part weight, 4 σ) that persists ≥ 2 samples; parts = drop / part weight; rises are refills | recall, precision, exact part count, lag per sensor |
| 3 Timing | `estimate_process_times`: each process starts with the pick of its first component; the last ends with the camera's `unit_complete` | model vs estimated vs truth, per process |
| Calibration | `calibrate_data` writes a new data file with measured means/CVs | apply to the working data or download YAML |

Sensor meaning (bin → component → part weight) is always looked up in the **current**
configuration, so after moving P3 to S2 the pipeline automatically uses LC_24 / LC_25.

The *Emulated physical testbed* mode runs the line with process times that secretly deviate from
the data file; calibration from the sensors then recovers them (typically from ≈ 12 % to ≈ 1–2 % error).

**Real data.** Upload CSVs in *Sensors & calibration → Uploaded CSV*:

- load cells: `timestamp` (or `t` in seconds), `sensor`, `weight_g`
- camera (optional, needed for timing): `timestamp`/`t`, `station`, `action`
  (`start_work` / `pick` / `unit_complete`), `has_frame`

Both files are put on one clock before analysis.

## Modelling assumptions (worth knowing)

- Single-piece flow: one unit (carrier) moves through the stages; a process that merges several
  subassemblies is flagged (only the carrier is tracked).
- Stage 1 always has raw material available; component supply is through the bins.
- Failures happen between units (not mid-job); repair time is drawn from the data file.
- Defects are recorded (FPY) but no rework loop is modelled.
- Sensor-based times include any waiting for material inside a job.

## Relation to the earlier `manual_line_sim.py`

| Before | Now |
|---|---|
| `StationSpec(name, mean_ct, cv, defect_risk)` in Python | stations/processes in the config file; times and defects per **process** in the data file |
| 5 fixed buffer numbers | `buffers:` objects between routing stages (any number of stations, parallel stages) |
| wearables + posture-driven defects | replaced by the document's sensors: 5 load cells per station + camera |
| camera dropout per log row | camera events (start, pick, unit complete) with dropout + confidence |
| bottleneck = longest mean cycle time | bottleneck = highest active share (accounts for blocking / starvation) |
| heap re-sorted on every insert, O(n) QC log scans | `heapq.heappush`, O(1) per event |
